# #60 F4 目录保存校验

适用现有 `POST/PUT /admin/dish`、`POST/PUT /admin/setmeal`。四个保存入口均需有效管理员签名且 subject=admin；普通用户签名或 user subject 拒绝。保留 token、字段、ID、业务 code 和 [管理端接口](余味居-管理端接口.html)。小程序继续通过原目录/购物车/下单接口读取；不改变可信计费或历史订单图片。

- `price` 为现有 SQL `DECIMAL(10,2)`，允许 0 至 99999999.99，最多两位有效小数；1.000 等可精确存储的值合法，0.001 不允许静默舍入。
- 菜品 `categoryId` 必须存在且 `type=1`；套餐分类必须存在且 `type=2`。不要求分类在售，不修改分类变更规则（F5）。
- 套餐有效 `setmealDishes` 非空，每项必须非 null，`dishId` 必须存在，`copies` 为 1 至 2147483647 的整数；空项、缺字段、缺菜品、小数或溢出均拒绝，不过滤后成功。兼容整数字符串；小数字符串拒绝。组成菜停售仍可加入独立起售的套餐。
- 新建仍需名称、分类、价格和套餐明细。PUT 保留当前部分更新：null/省略分类与价格沿用原值，null/省略套餐明细沿用原明细；校验更新后的有效分类、价格及明细。显式 `[]` 拒绝。旧库中已无效的关联/份数在部分更新时也拒绝，需提交合法替代值；不自动清理原数据。
- 原管理端创建/编辑发送完整主要字段及套餐明细，份数原样保留（#56）。菜品口味继续沿用原替换规则：null/省略口味清空口味；本票不改变该语义。图片、描述等继续沿现有 MyBatis 非 null 更新语义。

失败仍返回现有 `ApiResult`：`code=0, success=false, message=msg`（例如“请选择有效的套餐分类”），`data=null`。校验失败使用现有 HTTP 成功响应中的业务错误结构；畸形 JSON/非法份数也返回友好错误，不暴露反序列化/数据库详情。Controller 激活 Jakarta 校验，Service 同时检查业务不变量，直接调用不能绕过。

管理端原 `request` 按 code 抛出携带响应体的 `ApiError`，页面用 `ElMessage.error(error.message)`；失败不导航、不提示成功，保留输入和套餐份数供修改。两处原价格规则放宽为允许零，其余界面与请求链不变。

多表保存仍经现有 Service 的 Spring 事务；主表、明细删除及新增任一数据库失败全部回滚。关联套餐的菜品仍禁止删除。零价条目按原可信规则收费：服务端重读单价、每份包装 1 元、每单配送 2 元；单份零价商品总额 3 元，不采纳客户端金额。目录单价上限合法不代表任意数量与费用相加后都可下单；下单仍按现有总额上限拒绝溢出。

回退：用审查后的普通反向变更撤回目录规则、DTO 校验和两条表单规则及相应文档，不迁移 schema、不修复/删除原数据；保留本票补齐的四个保存入口管理员 subject 检查（JwtAuthInterceptor/CatalogSaveAuthTest）。客户端仍使用同一路径/响应；不撤销可信下单、关联删除保护、历史图片或购物车恢复。不要直接反向撤销包含该认证修复的整个提交。
