# 余味居改进计划执行顺序与依赖矩阵

## 目的

本文件是以下五份 ExecPlan 的总控文档：

1. [立即清理并轮换敏感凭据](./ExecPlan%20-%20立即清理并轮换敏感凭据.md)
2. [统一三端接口与环境配置](./ExecPlan%20-%20统一三端接口与环境配置.md)
3. [拆分后端业务边界](./ExecPlan%20-%20拆分后端业务边界.md)
4. [把 AI 从“同步调用模型”升级为可运营系统](./ExecPlan%20-%20把%20AI%20从“同步调用模型”升级为可运营系统.md)
5. [补齐生产级可靠性与质量门禁](./ExecPlan%20-%20补齐生产级可靠性与质量门禁.md)

执行原则是：安全改动先于功能改动，接口契约先于客户端迁移，分布式可靠性先于 WebSocket 归属迁移，AI 运营化先于模块边界最终收敛，最大范围的后端边界拆分最后进行。各计划可以在不同工作分支并行准备文档和测试，但同一文件的生产代码只能由一个计划在一个时间窗口内修改。

## 总体顺序

```text
P0 凭据清理与轮换
  ↓
P1 接口契约/环境配置 ─────┐
  ↓                       │
P2 可靠性、WebSocket、CI ──┼──→ P4 后端业务边界收敛
  ↓                       │
P3 AI 运营化 ──────────────┘
```

实际执行分为六个阶段：

### 阶段 0：安全止血，立即执行

先执行 P0 任务 1 和任务 2。只要发现任一凭据出现在 Git 历史、GitHub push、Fork、构建产物或日志中，就直接按“已泄露”轮换，不等待扫描工具重复确认。清理当前文件、历史和外部平台撤销必须形成一组可审计结果。

### 阶段 1：建立契约和配置基础

执行 P1 任务 1、P1 任务 2、P1 任务 3。此阶段冻结 HTTP/WebSocket 字段、admin/user `authScope`、环境地址和错误结构。P1 的 OpenAPI 静态门禁可以先做；运行时 Schemathesis 需要测试数据库和可启动后端，可在阶段 3 的 CI 基础上完成。

### 阶段 2：可靠性基础和自动化门禁

执行 P2 任务 1、P2 任务 2、P2 任务 3、P2 任务 4。这里先完成 Redis 协调、WebSocket ticket、连接重连、幂等键、订单版本锁、Actuator 和 OTel 基础接入。P1 任务 4 的小程序 HTTP wrapper 可以与 P2 任务 5 并行，但两者都不得各自实现 WebSocket 握手；握手只能由 P2 提供。

### 阶段 3：AI 运营化

执行 P3 任务 1、P3 任务 2、P3 任务 3，再执行 P3 任务 4、P3 任务 5。先完成脱敏评测集和 Spring AI 1.1.x adapter，再引入结构化输出、业务语义校验、工具前置 guard、流式、限流和成本记录。P3 与 P2 只可在不同文件上并行；共同修改 `pom.xml`、`application.yml`、AI Controller 和 CI 文件时必须串行合并。

### 阶段 4：运行时契约和三端回归

执行 P1 任务 5、P2 任务 5、P2 任务 6、P3 任务 6。此阶段运行后端服务、Schemathesis、管理端测试、微信开发者工具编译和真实沙盒回归。CI 全绿仍不等于小程序已通过官方编译，发布前必须完成人工清单。

### 阶段 5：后端边界收敛，最后执行

执行 P4 任务 1、P4 任务 2，再依次迁移菜品/购物车、订单/客服、AI/分析/风控。P4 任务 4 的 WebSocket transport adapter 归属必须在 P2 的分布式协调、ticket 握手和故障测试完成后执行。非关键通知使用 `AFTER_COMMIT`，关键事件在主事务内写 outbox、提交后 relay 发布；模块迁移不能把可靠性代码退回单机实现。

## 依赖矩阵

| 计划 | 必须先完成 | 可并行准备 | 不可并行修改 | 完成门槛 |
|---|---|---|---|---|
| P0 凭据 | 无 | Code Style Guide、依赖清单 | 无 | 外部新凭据验证、旧凭据撤销、历史/工作区扫描通过 |
| P1 接口与环境 | P0 的 Secret 注入方式 | P2 的故障测试设计、P4 的模块地图 | WebSocket 握手实现、同一份 `application.yml` | OpenAPI 静态门禁、核心运行时契约、三端配置检查 |
| P2 可靠性 | P0、P1 的 authScope/环境约定 | P3 的评测集、P4 的边界盘点 | `CustomerServiceWebSocketServer.java`、WebSocket 配置、CI 工作流 | 双节点、Redis 降级、Toxiproxy 分区、幂等并发测试 |
| P3 AI 运营化 | P0 的新 AI Key、P1 的错误/流式契约 | P2 的 OTel 基础、P4 的 AI 模块地图 | `AiModelServiceImpl.java`、AI Controller、同一 POM 配置区 | 结构化+业务校验、工具 guard、降级、计费取消、评测指标 |
| P4 后端边界 | P2 WebSocket、P3 AI port、P1 API 稳定 | 只可并行做只读依赖分析 | 迁移中的业务包、事件表、Mapper 所有权 | ArchUnit 真实拦截违规、outbox 重放、三端回归 |

## 文件冲突清单

以下文件必须指定唯一变更负责人并按阶段合并：

- `yuweiju-backend/pom.xml`：P2、P3、P4 都可能加依赖，先汇总版本矩阵再修改。
- `yuweiju-backend/src/main/resources/application.yml`：P0 负责 Secret 外置，P1 负责环境地址，P2 负责观测配置，P3 负责模型 profile；使用分段提交，禁止互相覆盖。
- `yuweiju-backend/src/main/java/com/codeying/websocket/CustomerServiceWebSocketServer.java`：先由 P2 完成分布式协调和握手，P4 只做 adapter 归属。
- `yuweiju-backend/src/main/java/com/codeying/service/impl/AiModelServiceImpl.java`：P0 先完成 Key 审计，P3 再替换 provider adapter，P4 最后迁移模块包。
- `yuweiju-web-vue/yuweiju-admin/src/api/http.ts`：P1 先统一请求/鉴权/错误，P2 只补可靠性测试，不能各自重写。
- `yuweiju-weixin-miniapp/pages/customer-service/index.js`：P1 迁移 wrapper，P2 只接入已有 ticket/重连协议。
- `.github/workflows/*.yml`：P0 Secret Scan、P1 契约、P2 质量门禁、P3 评测必须合并成有序 job，而不是多个工作流互相绕过。

## 共同验收门槛

每个阶段结束必须执行：

```text
凭据扫描 → Maven 测试 → 管理端 lint/typecheck/test → OpenAPI 静态检查
→ 运行时契约/集成测试 → 小程序配置检查 → 官方工具编译与人工发布清单
```

任何阶段都不能以“后续计划会修复”为理由关闭安全、鉴权、幂等或数据一致性失败。计划之间若发现接口字段、Token、事件名、数据库迁移或测试环境冲突，优先更新本矩阵和受影响计划，再继续实现。

## 回滚原则

P0 不能通过代码回滚旧 Secret，只能按外部平台双凭据窗口恢复并重新轮换。P1 保留旧 HTTP 路径和字段的兼容窗口，客户端可回滚 bundle。P2 的 Redis 协调失败进入明确单节点/拒绝策略，不能回滚到未声明的静态 Map 分布式模式。P3 用 feature flag 切回规则推荐/旧 adapter，调用记录保留。P4 每个模块迁移使用可构建小提交，数据库只做向前兼容迁移，事件通过 outbox 重放。
