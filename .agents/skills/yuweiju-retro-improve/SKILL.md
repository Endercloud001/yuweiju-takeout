# 实施复盘改进

输入：retro文档、用户选定条目及顺序、目标仓库、资源和GitHub权限。用户明确要求按建议顺序实施可作为条目选择；仅写“retro”或请求复盘文档不授权改造。读取事实与会话补齐输入，只询问无法确定的事项。

1. 判断是否明确要求“在新聊天/对话实施”。明确要求时先查真实 `create_thread` 工具，创建用户可见维护聊天，携带精简交接，原聊天返回链接并等待该聊天进展；工具不可用时给可复制交接并准确说明未创建。只请求实施时在当前聊天工作；子代理不是用户可见新聊天。完成：执行位置符合用户请求，普通文档请求没有创建聊天或启动AFK。
2. 读根AGENTS、[workflow](../../../docs/agents/workflow.md)、retro及相关实施报告，核对实际 checkout/HEAD、最新已确认main、脏状态、runtime来源和资源停止记录。先逐项检查当前实现，包括#13等已有改进；列“已解决跳过/本轮实施/未选/受阻”及具体证据。完成：每个选定条目有现状与可验证缺口，历史旧checkout不作为当前能力判断。
3. 新维护工作默认从已确认main在项目 `.scratch/` 建独立 `codex/` 工作树；当前聊天已具有合适隔离工作树就复用。写可评审方案，说明三端影响、范围、验证与回退；工具默认不变，优先复用既有普通检查和统一verifier。只有具体失败场景且Git、版本、主键、事务、唯一约束、类型和普通测试不足才考虑项目禁止默认新增的机制。完成：业务接口/schema/数据边界及用户修改保留，维护授权独立明确。
4. 按选定顺序逐项复现具体失败、实施最小修正并验证；技能逐个做应用场景测试，脚本用已有smoke/lifecycle入口。保存项目内证据、工作目录、退出码、实际业务结论、停机结果和未执行项。已有检查通过且相应源码未变就复用证据；新变更、失败或新疑点才追加检查。完成：每个实施项有验证支持；文案更新不能冒充监督器行为已修改。
5. 汇总逐项改动、验证、已跳过项、未完成及恢复入口。提交/推送/维护PR/合并/部署只按本维护任务实际授权；不继承业务票发布权限。结束只记录确有新证据的后续问题，由用户决定下一次维护。完成：成果可审查，资源状态明确，业务issue未被重开或被维护流程拖回。

交接内容仅携带：目标、已选条目、证据路径、已确认main、原工作区脏状态、资源归属、完成条件、授权。凭据不进入交接，完整聊天与大日志按需读取。维护不默认启动真实AFK或访问原业务库。

用户明确要求新聊天而工具不可用时，给交接后等待用户选择执行位置，不自行降级为当前聊天实施。

示例：`使用 yuweiju-retro-improve，在新对话实施 docs/某票-retro.md 中已选1/2/3项；允许项目内隔离无模型验证，GitHub写入另定。` 若没有“新对话”请求，本技能在当前聊天完成维护。
