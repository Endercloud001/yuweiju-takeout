4. 最近最难维护的 1–3 个具体事件是什么？说明要改什么、卡在哪里、花费多久以及业务后果；若只是阅读或启动困难也可如实说明。

## 第三轮：架构与验收边界

架构研究已完成，见 [官方来源研究笔记](./yuweiju-architecture-research.md)。结论是 Spring Boot 不强制固定三层；应用服务是用例编排职责，不必是统一第四层；模块化单体的目录/依赖组织可与分层并存；六边形架构关注外部设施隔离。官方示例不证明行业采用比例。Vue 前端无须照搬后端 Controller/Service/Mapper。

根项目仍要求遵守后端规则。现有 `.trae/rules/rules.md` 1.2 强制分层包结构，2.1 强制 Service/DAO 对外接口；全面改成业务包不能直接视为合规，必须形成明确决定并在后续计划中说明规则修订。本轮不改规则、业务代码或 schema。

本轮全部是建议，未被接受前不记为用户决定：

- Q9（调研后复问）：更希望保留现有全局分层包、整理命名与职责，还是采用按业务模块组织、模块内按需分层的单体？推荐优先验证后者，普通 CRUD 不增加空转服务，复杂下单/推荐按需编排，仍可单应用共享 MySQL；全面移动目录之前以一个复杂查询的可理解性与兼容性验证收益。
- Q15：热度分析与异常订单识别的验收，是保留现有训练/预测能力且能解释流程，还是允许调整算法，只保留可解释输出？推荐保留能力，先验证可运行与解释性；只有证据表明旧实现不适合时才替换算法，不以演示数据宣传真实效果。
- Q16：样式保留是否要求所有页面视觉完全一致，还是主要布局/颜色/素材/交互保持一致，允许必要的错误、降级说明小变化？原小程序源码已无法取回，是否接受内部重新实现但保留外观？推荐允许内部恢复/重建，逐页面人工对照现有界面，允许明确的故障说明；不建立额外视觉 baseline 或 gate。
- Q17：DeepSeek 额度、网络或模型输出失败时，是只提示重试，还是用在售候选生成明确标注的非模型推荐？推荐有可售候选则返回可解释候选且标明降级，无候选则明确告知；天气失败只省略天气因素，恢复后再次优先真实模型。不会绕过归属与可售校验。

## 判断标准与三路线比较

### 第四轮：继续核对访谈缺口

用户要求继续研判仍需 grill-with-docs 的事项。上一轮“访谈已收敛”过早：架构已确定，路线尚未被采纳，业务语义和智能验收仍有可改变重构范围的决定。本轮不重问技术偏好、原库使用、前端样式、DeepSeek 失败提示或常规分层。

- Q19：是否把“保留技术栈的局部重构”作为默认维护路线，最小验证结果不支持时再调整；还是验证完成前仍并列保留三种路线？推荐以前者收窄判断，但这不是开始修改代码的许可。

### 第五轮前置调查：风险识别不等于用户封禁

以下均为静态核查，未运行服务或查询数据库，路径以 `yuweiju-backend/src/main/java/com/codeying/` 为根。

### 既有判断标准

## 推荐范围与理由

此前证据更支持 **保留技术栈的局部重构，后端常规分层，小程序按需内部恢复或重建**。按 Q19，它保留为待验证的候选推荐，不能作为默认已采用路线；先完成最小验证，再重新比较三路线。

- 后端：让 Controller、Service、Mapper 职责明确；复杂筛选和聚合查询具有可搜索入口，结合后端规则 11.1 评估 SQL 放置。检查订单查询写回图片的语义，明确下单与风控/推荐的耦合；已有 ApplicationService 按职责评估合并或保留。
- 管理端：保留 Vue、TypeScript、现有外观和可复用 API/状态结构；围绕具体业务梳理，不因维护者不熟悉就全面换框架。
- 小程序：原始源工程不可恢复是主要特殊成本。保留当前页面外观与业务，在可编辑、可重建实现中逐页恢复；具体是否继续 uni-app 或局部原生实现属于后续技术验证，不在本轮假定。
