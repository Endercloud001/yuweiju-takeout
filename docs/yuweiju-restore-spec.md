# 余味居首期局部修复与可维护性恢复规格

日期：2026-10-05（Asia/Shanghai）。范围依据：恢复访谈 Q1–Q7，Q7 已接受整体范围。测试边界：维护者在本次 to-spec 核对中明确接受并授权发布。本规格记录需求与验收，不是 ExecPlan，也不授权实施、迁移或正式发布。

## Problem Statement

余味居现有三端可以完成代表性的点餐履约、模拟支付、人工客服和真实 DeepSeek 推荐，但用户仍会遇到结算与实记金额不一致、模型失败却出现菜品推荐、历史订单图片被查询改写、智能附加依赖故障阻断核心业务、未产生训练/预测结果却提示完成的问题。维护者也难以从入口找到业务查询、事务与失败路径；小程序只剩编译产物，尚不能证明受影响页面可从可编辑实现重建。

### 问题、复现场景与行为要求

| 项目 | 复现场景与当前行为 | 预期行为及证据边界 |
| --- | --- | --- |
| A1 金额一致 | 小程序单份 18 元商品结算显示 25 元，订单 974 落库 19 元；客户端加配送费 6 元，服务端只加客户端 packAmount，缺失值取 0 | 新单商品合计 + 每份 1 元打包费 + 固定配送费 2 元；该单份商品应为 21 元。服务端从可信商品与数量计算、校验费用，结算/提交/详情/管理端与落库一致；旧订单 974 仍为 19 元 |
| A2 模型失败语义 | 模型返回 HTTP 200/非 JSON 内容时，小程序仍显示候选菜卡；原解析失败分支构造候选推荐。真实合法推荐及本地上游 503 重试提示已有证据 | 合法输出正常展示；无效内容、非法候选、503、额度不足和超时只提示重试，不用候选冒充模型成功；天气缺失不阻断合法推荐。402/超时及持续失败保护仍需补验 |
| A3 历史图片 | 内存案例让历史图与当前图不同或历史图为空，原查询图片处理都会换成当前图并调用写回 | 已有历史订单图片保持不变；缺失只作展示兜底，不查询补写。当前原库没有缺图，不以 URL 抽样可达证明语义正确；不承诺恢复已被覆盖且无原始证据的图片 |
| A4 智能故障隔离 | 推荐统计 Redis GET 异常传播到提交并导致 SQL 回滚；管理员详情的风控结果读取异常令查询失败。原评分主体 Mapper 故障的下单案例已隔离通过 | 推荐统计失败不阻断正常下单/购物车；风控附加读取失败时管理员仍能读取合法订单，风险状态如实不可用。核心订单数据库故障仍失败并保持事务，不吞权限拒绝；分页风险装配同类路径需要检查，不能写成已运行复现 |
| A5 执行状态 | 无快照预测仍返回“任务完成”；风控样本不足跳过仍返回 triggered。部分热度训练已有 executed 判断，不能称所有跳过路径都错误 | API/UI 区分已触发、执行中（若适用）、实际完成、跳过、无数据、模型不存在和失败；报告实际产出与原因。历史模型存在或触发成功不等于本次训练成功；效果指标另行解释 |
| B1 本机启动 | 原 jar 默认启动两次发生 Windows 临时目录相关 socket 错误；加短临时目录参数后同一 jar 成功启动 | 提供适用环境、前置服务、命令和停止方式明确的可复现步骤；保留已验证参数，不借此换 JDK 或认定业务缺陷 |
| B2 管理端检查 | 完整 lint 有 22 errors，集中于两个 CommonJS 脚本；src lint 与 build/typecheck/test 已通过 | 按 Node/CommonJS 实际语义修脚本与 ESLint 适配；完整 lint/typecheck/test/build 通过，不整体关闭检查 |
| B3 职责与规范 | 购物车、地址入口承担状态/事务，订单分页在 Service 拼条件及风控子查询；其他业务同样存在分散条件、大服务混合算法与 IO。薄 Controller/BaseMapper 继承本身合理 | 全部后端业务逐组检查并按真实职责恢复；全部业务筛选/统计与条件持久化通过具名 Mapper。入口不承载业务事务，Service 保留规则与事务；不以三层行数相近验收 |
| B4 小程序恢复 | 13 页编译产物已能在模拟器联动；结算页仍为 webpack 产物，缺少原可编辑源工程，未证明重新构建及缺图视觉 | 优先恢复结算、历史/详情及必要依赖为可编辑、可编译实现；保持其他页面联动与既有外观。共享 runtime/vendor 阻碍局部恢复时带证据重新讨论，不自动全量重建 |

## Solution

保留技术栈、常规 Controller/Service/Mapper 分层、原库 schema/数据/ID 和两前端现有外观，以具体用例一起完成职责恢复和 A1–A5 修复。最高优先是全部后端业务职责恢复及统一规范，配套完成本机启动说明、管理端现有检查和小程序受影响页面恢复。

### 首期覆盖

后端逐组覆盖：身份/员工与登录；分类/菜品/口味/套餐；购物车/地址；订单/模拟支付/履约；人工客服；AI 助手/天气/模型调用；热度/分群/训练预测；异常订单评分/训练/反馈；统计报表/工作台/店铺状态；上传/默认图片。任务和 WebSocket 是对应业务入口，同样受职责与安全要求约束。旧模板管理页调查实际启用状态与认证边界，不擅自删除或更改认证。

“全部覆盖”要求每组有检查结论、必要修复与代表回归，合理代码允许无 diff。保留点餐履约、人工客服、AI 推荐、热度分析、异常订单识别五项能力；首期要求可运行、可解释、真实表达状态，不要求算法质量优化达标。

## User Stories

1. 作为点餐用户，我希望结算和实记金额一致，以便在提交前知道实际费用。
2. 作为点餐用户，我希望多份菜品与套餐按同一规则计费，以便理解打包费和配送费。
3. 作为历史订单用户，我希望原订单金额不被新规则改写，以便保留演示记录。
4. 作为用户，我希望失败的模型请求提示重试，以便识别推荐当前不可用。
5. 作为用户，我希望合法真实模型推荐继续展示，以便使用 AI 推荐能力。
6. 作为用户，我希望天气缺失仍能获得合法推荐，以便天气依赖不影响点餐。
7. 作为用户，我希望非法或停售推荐不会进入购物车，以便保留现有可售校验。
8. 作为用户，我希望只能访问自己的会话和订单，以便保持归属隔离。
9. 作为历史订单用户，我希望看到下单时已有图片，以便当前商品换图不改变历史展示。
10. 作为用户，我希望缺图仍有可加载的兜底，以便原布局保持可用。
11. 作为点餐用户，我希望推荐统计故障仍能正常下单，以便附加能力不阻断核心流程。
12. 作为管理员，我希望风控读取故障时仍能看订单，以便继续履约并知道风险结果不可用。
13. 作为维护者，我希望核心业务写入失败完整回滚，以便不产生部分订单。
14. 作为管理员，我希望训练与预测显示真实执行状态，以便不把跳过当成产出。
15. 作为管理员，我希望无样本、无模型与失败分别说明原因，以便采取合适的后续操作。
16. 作为管理员，我希望看到模型窗口、版本和效果限制，以便不把旧模型指标当成本次成果。
17. 作为用户，我希望首页、模拟支付、客服和 AI 在局部页面恢复后继续联动，以便保持现有体验。
18. 作为维护者，我希望能修改并重编译受影响小程序页面，以便后续修复不依赖手改编译产物。
19. 作为维护者，我希望能从每组入口找到具名查询，以便定位筛选、分页和统计口径。
20. 作为维护者，我希望规则、事务、算法与 IO 的职责明确，以便修改一个用例时理解失败影响。
21. 作为维护者，我希望统一规范与当前包结构、校验和分页技术一致，以便按现有项目继续开发。
22. 作为维护者，我希望本机启动和管理端检查可复现，以便可靠地开始开发与验证。
23. 作为维护者，我希望清楚正常演示对数据库、Redis 和模型文件的写入，以便避免误清原资产。
24. 作为维护者，我希望完成查询、事务和失败路径练习，以便能独立讲解并做一次小修改。

## Implementation Decisions

- 已接受 ADR 0001 的常规分层和 ADR 0002 的历史图片语义；技术目录不是不同业务上下文，统一使用“演示数据”“模拟支付”“历史订单图片”。
- Controller/任务/WebSocket 处理协议、身份上下文、参数与响应；Service 负责业务规则、用例与事务。归属、可售与状态规则在复用用例中仍有效，不能搬层后仅靠单个入口保护。
- 全部业务筛选、统计和业务条件更新通过具名 Mapper；简单查询可在 Mapper 内复用 Wrapper，复杂动态 SQL、聚合、Join/子查询用 XML 和参数绑定。标准主键 CRUD 保留 BaseMapper；Service 决定状态规则与是否允许更新，不构造业务数据库条件。
- 大服务按实际变化职责整理，算法计算、模型文件、外部 HTTP 和缓存职责明确；已有 ApplicationService/实体 Service 按真实责任保留或合并，不机械增加第四层、不为每个私有方法造接口。
- 新单收费规则已确定，服务端计算和校验，金额使用 BigDecimal 与一致舍入口径。客户端 packAmount/总价不能作为可信收费依据。具体舍入、范围校验、旧调用费用不一致时的兼容处理以及报价展示方式，由后续 ExecPlan 核查现有调用点后明确，不在本规格擅定新增接口或字段。
- 历史查询不覆盖/补写订单图片；缺失在展示层兜底。旧单费用从原持久化数据展示，不套新规则重算或伪造历史费用明细。
- DeepSeek 优先真实模型；失败只提示重试，不以候选补推荐冒充成功。天气独立查询，保留会话归属、在售检查和人工客服边界。
- 隔离智能附加故障与核心数据库故障。必须说明 SQL、Redis、模型文件及外部调用各自失败边界，不能把 SQL 回滚说成所有副作用回滚；具体隔离实现留给计划，不自动引入 outbox、队列或新中间件。
- 热度/风控保留现有算法、阈值与能力，如实报告执行和效果。评分及订单级人工 reject 不等于用户级封禁。
- 统一规范集中在 `docs/standards/backend.md`，替代废弃后端规则，不新增并行强制规则；对齐实际单工程/包名、Jakarta、MyBatis Plus 分页、ApiResult/PageData。保留 DTO/Query、VO、Entity 职责、构造器注入、资源关闭、友好异常、cause 和日志脱敏；不因旧模板强制拆模块、改响应名或退回旧校验 API。
- 首期小程序只恢复受影响页面及必要共享依赖，保留其他页面联动和外观；恢复入口与编译技术方案必须先调查。管理端沿用目录、Element Plus、严格 TypeScript、请求和视觉规则。

### 三端影响与兼容要求

| 端 | 影响 | 兼容要求 |
| --- | --- | --- |
| 后端 | 全部业务职责；金额、图片读路径、推荐失败、附加故障隔离、训练/预测结果表达 | 公开路径、字段、类型、业务 code、分页/排序/时间口径及认证/归属保持兼容；必要响应调整先列消费者及兼容方案。原 schema/ID 不变，不把本规格当迁移授权 |
| 管理端 | 新旧订单金额/图片、风险不可用提示、统计页训练/预测状态、正常登录与现有 lint | 保留请求 token、VITE_API_BASE、code === 1 判断、路由约定和外观；不只凭 HTTP 200 显示成功，新增状态不能误导旧消费者 |
| 小程序 | 结算、历史/详情与依赖；推荐失败显示及全链路回归 | 保留用户 authentication 鉴权约定、已有登录/归属、模拟支付和页面联动；不得统一成管理员 token 字段，不默认重建所有页面 |

## Testing Decisions

维护者已确认：主要从既有 HTTP/WebSocket 与三端页面检查外部行为；复用 Service/Controller 测试与独立故障注入材料补失败案例；真实查询/事务经 Spring 代理和数据库验证。普通自动化测试使用隔离数据，原库只做已规划的正常演示并记录写入。没有新增私有方法测试层或架构 gate。

好测试检查用户可观察结果、权限、持久化与副作用，不锁定类数量、私有方法、Wrapper 字符串或代码搬迁形式。原订单风险测试中 SQL 片段断言不能证明新 Mapper 查询正确，应围绕筛选结果验证。当前名为 IntegrationTest 的订单/风控测试使用 Mockito，不作为真实事务证明。

### 正常、异常与缺失数据验收

| 项目 | 正常 | 异常/拒绝 | 缺失数据与边界 |
| --- | --- | --- | --- |
| 金额 | 单份 18 元=21 元；多数量、菜品/套餐组合各端及落库一致，打包按商品份数计算 | 篡改总价/打包费不影响可信收费；非正数量、负价等不生成错误订单；失败无部分明细或错误清购物车 | 空车、缺商品/地址/金额/数量友好处理，不把缺失值默认为可下单的零价；具体拒绝与校验文案在计划明确；旧单 974 仍 19 元 |
| AI | 真实合法 DeepSeek 推荐在小程序显示合法菜卡，用户可正常操作 | 503、无效内容、非法候选、超时、额度失败提示重试且无冒充推荐；会话越权和停售仍拒绝 | 天气 null 不阻断合法输出；缺历史或无可售候选如实提示，不能靠伪造推荐制造成功；持续失败调用控制调查后做最小保护 |
| 图片 | 改当前商品图后各订单查询仍显示已有历史图，查询前后明细值相同且不发生图片写回 | 无权限查询仍拒绝；图 URL 加载失败有可用展示，不改库 | null/空图有兜底，用户历史/详情和管理员分页/详情保持布局；缺图/换图用隔离案例，不故意破坏原库 |
| 隔离/事务 | 正常订单、购物车、履约与风险结果可用 | 注入推荐统计 Redis GET、管理员风险读取异常，核心业务仍成功且风险不可用；核心订单/明细写入故障仍失败、经实际代理验证 SQL 原子性 | 无推荐上下文/无风险结果不伪造低风险；覆盖附近曝光/点击/转换及分页装配；分别检查 Redis 已写后失败，记录未回滚副作用 |
| 热度/分群 | 有效历史窗口完成实际快照/训练/预测，核对窗口、模型版本、数量及结果 | 非法日期/参数友好拒绝不暴露堆栈；执行依赖失败如实失败，不发完成提示 | 无快照、样本不足、无模型区分提示，不造有效结果；部分成功按实际阶段说明，未成功训练不覆盖为成功 |
| 风控 | 普通/异常候选可评分解释，实际新训练成功案例有模型与结果证据 | 保留订单级反馈/拒绝语义和权限；未标注候选不能宣称模型排序错误 | 当前窗口样本不足只记跳过；先调查可验证数据/窗口，不用跳过或旧 ACTIVE 模型代替本次训练成功，不能批量造原库训练数据来通过 |
| 职责/查询 | 每组有代表调用链与具名查询；筛选/分页/排序/统计时间边界和口径保持一致 | 每组验证权限拒绝及相关失败；事务移入 Service 后验证代理调用，不能只新增注解 | 无记录/空页/空统计结果正确表达；合理薄类可保留；全业务检查结论不等于全状态分支已通过 |

既有先例包括订单风险装配测试、AI 意图路由测试、风控规则/模型测试和分析 Controller 训练测试。既有分析测试已有“训练跳过不执行预测”案例，继续按真实结果扩展。管理端格式化测试只有两例，不作为业务 UI 覆盖；复用现有浏览器、WebSocket、开发者工具页面操作证据和故障材料补受影响回归，材料不是新门禁。

### 小程序源工程与外观验收

1. 结算、历史/详情及必要依赖有明确可编辑入口、编译命令和环境说明；从保存的实现重新编译，在微信开发者工具模拟器运行，并保留完整编译结果。只通过 node --check、页面文件齐全、手改 vendor 或旧产物能运行不算源工程恢复。
2. 对受影响页面取得可查看的同场景前后截图，核对布局、颜色、字体、商品图尺寸、费用区、按钮和交互；使用既有素材，必要费用/状态说明小调整单独解释。现有自动截图超时和页面数据证据不能当成视觉验收，可用实际可查看截图与人工对照完成，不新增像素差异 gate。
3. 正常商品、缺图、失败提示、历史订单分别检查；首页→结算→模拟支付→管理端接单/配送/完成→用户历史/详情，以及客服双向消息、合法 AI 推荐继续联动。
4. 调查共享 runtime/vendor 后如无法局部隔离，说明具体依赖与最小扩大范围，重新核对后才能扩大；未恢复页面源工程不宣称已全部恢复。

### 常规检查与维护者练习

- 后端 package 与受影响普通测试通过；管理端完整 lint/typecheck/test/build 通过；小程序受影响实现重新编译运行。管理员用正常密码登录进入演示，不把测试 JWT 当登录证据；现有模拟器 wx.login 证据不扩大为生产认证验收。
- 每组后端业务维护者能讲解一条入口→规则→具名查询→结果链路，指出权限、空数据、事务和依赖失败的处理位置。
- 查询练习：定位订单分页的状态/风险筛选，解释参数绑定、分页排序和报表时间口径；在隔离数据中做一次小筛选改动并用结果测试验证。
- 事务练习：说明下单的订单/明细/购物车写入，经过 Spring 代理注入核心写入失败，解释回滚结果、自调用限制和自增间隙。
- 失败练习：分别注入推荐统计 Redis、风险读取、坏模型输出，解释“订单成功但附加能力不可用”与“核心写入失败”的区别，指出 SQL 回滚不覆盖 Redis/文件/外部请求。
- 智能练习：阅读正常、异常、缺失数据结果，解释执行状态、模型版本、数据窗口、RMSE/MAE 与未标注风控候选的限制。按主要模块完成讲解及一次小修改；具体任务与数据安排在 ExecPlan 中落实，不以照念文档替代操作。

## Out of Scope

- 换栈、全目录移动、强制拆 Maven 模块、机械统一第四层、重写标准 CRUD。
- schema 迁移、清理原库、重建 ID、追改历史金额、擅自回填历史图片、恢复无证据的旧图。
- 真实支付退款、语音点单、用户级封禁、真机、公网发布、长期运营。
- 全小程序源工程重建、独立全项目性能优化、为未测量 N+1 开设性能项目；职责整理中的具体重复读取按行为风险处理。
- 算法调优、阈值/融合/标签优化及真实营业准确率达标；不为两个未标注候选调整模型结论。
- 自动采纳历史计划中的模块化单体、Spring AI、SSE、outbox、分布式改造、hash、冻结 contract、baseline 或新 gate。没有具体失败场景及普通工具不足的论证，不加入这些机制；已有安全措施与项目检查继续保留。
- 本轮业务代码、配置、规则文档修改、原库验证写入和迁移；本轮仅发布此规格 Issue，不发布其他历史建议。
